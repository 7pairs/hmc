# 0003 手動で依存性を注入する

- **ステータス** 採用

## 背景

選手、ルール、リーグ、半荘を扱う複数の画面から同じDBを使う。保存が失敗した場合や保存中に画面が再生成された場合をテストするため、画面の状態ホルダーに渡すRepositoryを差し替えられるようにする。

## 決定と適用範囲

共通Kotlinの `AppContainer` をプロセスごとに1つ持つ。Androidは `Application`、iOSはSwiftUIのアプリが保持するオブジェクトを所有者とする。各OSが用意したDBのビルダーを使い、コンテナがRoomのDBとRepositoryを組み立てる。状態ホルダーには必要なRepositoryをコンストラクタで渡す。状態ホルダーの寿命は画面の操作に合わせ、DBやRepositoryとは別に管理する。（参照：[半荘保存のアーキテクチャ](0004-define-match-save-architecture.md)・[初期画面の設計](../specs/initial-screen.md#設計)）

## 採用理由

検証用アプリで `Activity` と `UIViewController` をそれぞれ再生成しても、同じDBとRepositoryを使って保存済みの半荘を読み出せた。テスト用Repositoryへの差し替えで保存の失敗と再試行も確認できた。選手・ルール・リーグの管理と半荘の登録・更新が加わっても、共有する依存を `AppContainer` で組み立て、各画面の状態ホルダーに渡す構成を使えると判断した。（参照：[手順書0009の検証記録](../procedures/0009-save-matches.md#手順3の作業記録)）

## 見送った候補と見直す条件

アプリ全体から共有オブジェクトを直接取得する方式では、利用側が依存する実装をテストで差し替えるために共有状態の管理が必要になる。DIライブラリには依存の組み立てや寿命の管理を任せられるが、現時点で想定する構成は手動で組み立てる場所をまとめられる。寿命の異なる依存が増え、組み立てや解放の規則を追いにくくなった場合は、ライブラリの導入を再検討する。コンストラクタで依存を受け取る形を保てば、移行の主な変更は組み立て部分に集められる。
