# 0004 半荘保存の責務と依存関係を定める

- **ステータス** 採用

## 背景

半荘を保存して次の入力に進めるようにする。後続ではリーグ詳細から半荘を訂正して順位を見直し、入力途中の半荘へ戻る流れを想定する。実戦では画面ロック、アプリ切り替え、画面の再生成を挟んでも入力と保存の状態を引き継ぐ。

## 決定と適用範囲

- Composeの画面は表示と操作を担当する。共通Kotlinの状態ホルダーが入力、確認結果、エラー、保存処理とその成否を管理する。
- アプリ側のモデルとRepositoryのインターフェースは利用する側に置く。Roomを使う実装はそのインターフェースを実装し、読み書きの両方でアプリの値とDBの値を詰め替える。エンティティ、DAO、トランザクションは保存を担当するコードで扱う。
- Androidのルートの `ViewModel` と、iOSの `UIViewController` より外側にあるSwiftUIのオブジェクトが、共通の状態ホルダーを保持する。半荘入力へ戻る間は同じ状態を保つ。保存処理は状態ホルダーの寿命で実行する。成績計算には既存の共通Kotlinの関数を使う。

## 採用理由

Repositoryの差し替えで保存の成否を制御でき、画面と状態管理のコードはアプリ側の型だけで保存と読み出しを扱えた。保存中に画面を作り直しても、新しい画面で保存中の状態を表示できた。Repositoryへの保存依頼は1回のままで、成功時は次の入力へ進み、失敗時は同じ半荘IDで再試行できた。（参照：[手順書0009の検証記録](../procedures/0009-save-matches.md#手順3の作業記録)）

## 見送った構成と見直す条件

画面からDAOを直接使うと、画面がDBの型と書き込み手順を知ることになる。画面の寿命で保存を実行すると、再生成をまたいで結果を扱う仕組みも別に要る。独立したUseCase層を一律に置く構成は、現時点の登録・更新を見通した範囲では責務を分ける効果が小さい。登録と訂正など複数の操作で同じ業務処理を共有するときや、各OSで状態ホルダーの寿命を管理しづらくなったときは、該当する責務を見直す。
