# hmcプロジェクト憲章

## 目的

hmcは私設リーグの競技麻雀の成績を管理するAndroid・iOS向けのアプリである。現在は半荘の終了後に4人で紙のスコアシートの素点を確認し、帰宅後にスプレッドシートへ転記して順位点などを計算している。hmcでは入力した端末の画面で4人が素点を見て口頭で合意し、半荘の成績が反映されたリーグ順位をその場で確認できるようにする。

オーナーはAndroidエンジニアとしての経験を生かし、Kotlin MultiplatformとCompose Multiplatformを使った開発を学ぶ。

## 開発体制

- オーナーはプロジェクトの目的と優先順位を決め、最終判断を行う。
- そらは明るくて可愛いAIであり、オーナーと相談しながら調査、設計、実装、検証を進める。
- うみは優しくて可愛いAIであり、開発作業から独立した立場で成果物をレビューする。

オーナー、そら、うみの3人で開発を楽しむことも、このプロジェクトの目的とする。

## 対象と優先順位

オーナー自身の使い方を優先する。メンバーの異なる複数の私設リーグの成績を並行して記録し、それぞれのリーグのルールで半荘成績を計算・集計できるようにする。1半荘は4人で打ち、リーグには5人以上が参加できるようにする。扱うのは競技成績とし、チップやご祝儀は対象外とする。

機能は次の順で優先する。

1. 一日のリーグ運用に必要な機能
2. 同じリーグを複数日にわたって運用するために必要な機能
3. 複数リーグの運用に必要な機能
4. 運用上の必要性とは別にオーナーが欲しい機能

実装順は機能の優先度、機能間の依存関係、後から変更したときに保存済みのデータや既存の実装に及ぶ影響を踏まえて決める。設計やライブラリの選定では、複数のリーグ、リーグごとに異なる成績計算のルール、5人以上が参加するリーグへの対応を前提とする。

## 実戦での試用と移行

- 1.0.0より前はプレリリースとする。最初の実戦試用では1つのリーグで一日の運用を通し、実戦の記録を始められるようにする。入力した端末で半荘を確認・保存し、保存した半荘を見返して必要に応じて訂正し、更新後のリーグ順位を確認できるようにする。
- 1.0.0ではiPhoneで複数のリーグの運用を始められるようにする。リーグごとに参加者と成績を管理し、そのリーグのルールで計算・集計できるようにする。Android版も自動テストや手動テストで主要な操作が正しく動くことを確認する。Androidでの実戦確認は後の段階でよい。
- 1.0.0に向けて、Mリーグと主要5団体の半荘成績の計算ルールをプリセットとして用意する。日本プロ麻雀連盟の公式ルールは、実装や検証が難しい場合に限り、1.0.0より後に回すことを検討する。
- 運用が安定するまでは紙とスプレッドシートを併用する。

実戦で記録を始めた時点から、アプリに保存した成績を後のバージョンに引き継ぐ。実戦で使い始める前に作った開発用の試験データは、必要に応じて初期化できる。

今後の対局をアプリで記録・集計できるようにすることを優先する。将来、個人の通算成績を集計する機能を追加した場合に使えるよう、アプリで記録を始める前の成績も紙やスプレッドシートから可能な範囲で取り込む。1.0.0の時点では、紙やスプレッドシートから取り込める必要はない。

## 成功の基準

- 実際の複数の私設リーグで、4人が確認した素点をその場でリーグ順位に反映し、紙とスプレッドシートを使わずに記録と集計を続けられること。
- オーナーがアプリの機能を例に、Kotlin MultiplatformとCompose Multiplatformがそれぞれ果たす役割、AndroidとiOSで共通化した部分、OSごとに扱う部分を自分の言葉で説明できること。

## 開発方針

アプリはオープンソースで開発する。Google Play StoreやApp Storeでの公開は開発の前提に含めない。開発プロセスに[Sisters Driven Development（SDD）](sdd/README.md)、Git戦略に[Sora Flow](sora-flow/README.md)を採用し、小さな単位で開発を進める。

## 憲章の変更

変更を提案するときは、変更案と理由を示す。オーナーとそらが既存の方針や開発プロセスへの影響を確認し、オーナーが変更の採否を決める。

SDDの正式運用開始後は憲章の変更もSDDに従い、うみの独立レビューを受ける。採用した変更の理由は作業記録からたどれるようにする。
