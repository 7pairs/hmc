# 0006 文書とエラー文言の表記をそろえる

## 目的と対象

hmcの日本語文書で英数字と空白の表記、段落末尾の補足リンクの書き方をそろえる。素点入力のエラー文言2件は実装とテストの期待値、現行仕様書の文言表を一緒に更新する。手順ごとにコミットを分け、同じPRで取り込む。

完了済みの手順書は今回に限り本文の表記を整える対象に含める。当時の判断、結果、未対応だった事項を保ち、画面表示をそのまま記録した引用、入力値、ログの原文も保つ。（参照：[SDDの作業記録と文書の更新](../sdd/README.md#12-作業記録と文書の更新)）

同梱のSDDとSora Flowは画像の説明用READMEを含む4文書を確認し、表記を直す箇所は0件だった。両手法の文書は修正対象から外す。

## 手順

### 1. 文書の表記をそろえて記述ルールを追加する

そらは `docs/` 配下の対象文書に次のルールを適用し、`AGENTS.md` の日本語文書の指示に追加する。以降は新規文書と既存文書を編集した箇所に適用する。

- 地の文の英数字と、項目名と値を区切る空白は半角にする。完了済みの手順書も含め、「ステータス」と「作業ブランチ」の項目名と値の間は半角スペース1つにそろえる。正式な題名、原文どおりの引用、全角の文字や空白に意味がある入力例などは元の表記を保つ。
- インラインコードと地の文の間は半角スペース1つで区切る。行頭と行末、句読点との境目、括弧の内側には空白を足さない。
- 段落末尾の補足リンクは本文の句点の後に「（参照：…）」で添える。複数のリンクは同じ括弧の中で `・` を使ってつなぐ。文の一部として読めるリンクはその形を保つ。

既存文書の表記をそろえる際は `yomiyasu` を適用せず、言い回しや文の構成を保つ。この手順書の草稿や `AGENTS.md` に追加するルール文など、新たに書く日本語には従来どおり適用する。

素点入力の仕様書にあるエラー文言2件は手順2で更新する。

そらは差分を読み、文書の意味や当時の記録が保たれていることを確認する。書き方を変えた補足リンクと、表記を直した見出しへのリンクを確認し、参照先が変わっていないことを確かめる。うみは3つのルールの適用、元の表記を保つ箇所、リンク先を独立に確認する。二人で検証とレビューの結果を確認する。

### 2. 素点入力のエラー文言を半角数字にそろえる

そらは先に `ScoreConfirmationTest.kt` の既存テスト2件の期待値を変える。合計エラーの「４人」を「4人」に、同点エラーの「３人」を「3人」に変え、`./gradlew :shared:testAndroidHostTest` を実行する。両方のテストが文言の不一致で失敗することを確かめる。

次に、`ScoreConfirmation.kt` の表示文言と現行仕様書の文言表に同じ変更を入れる。全角入力を拒否する例の `３５０００` はテストと仕様書で元の表記を保つ。共通テストを再実行し、すべて成功することを確認する。（参照：[素点入力の仕様](../specs/match-score-entry.md#仕様)）

二人で素点の検証からエラー文言の表示までをたどり、エラー理由の判定と表示をどこで担うか、今回の変更がどこに影響するかを確認する。リファクタリングの要否と理由を作業記録に残す。（参照：[SDDの構造の見直しとリファクタリング](../sdd/README.md#10-構造の見直しとリファクタリング)）

うみはテストの失敗と成功の記録を確認する。実装、期待値、仕様書の文言が一致し、エラーの判定条件と全角入力を拒否するテストが保たれていることを確かめる。構造の見直しで判断したリファクタリングの要否と、その理由が妥当かも確認する。

二人で検証とレビューの結果を確認する。オーナーが変更した箇所とエラーの判定条件への影響を自分の言葉で説明し、二人で理解を確認する。

### 手順2の作業記録

そらは合計エラーと同点エラーの既存テスト2件の期待値を先に変更した。Android Studio同梱のJBR 25.0.4で `./gradlew :shared:testAndroidHostTest --console=plain --offline` を実行した。24件中2件が失敗した。期待値では半角だった数字が実際の文言では全角だったことをXMLレポートで確認した。

実装と現行仕様書の文言表を期待値に合わせて更新し、同じコマンドを再実行した。XMLレポートでは24件すべて成功し、失敗・エラー・スキップは各0件だった。全角入力の拒否例 `３５０００` はテストと仕様書に残した。

そらは素点の検証から表示までの流れを確認した。`calculateMatchResults()` がエラー理由を判定し、`ScoreConfirmation.kt` が理由を表示文言に変換する。画面はその文言を表示する。判定と表示の役割が分かれており、実装の変更は文言2件の数字に限られるため、二人でリファクタリングを見送ることにした。

うみは独立レビューで差分4ファイルを読み、文言2件が実装、テストの期待値、現行仕様書で一致することを確認した。エラーの判定条件と順序、`EXPECTED_SCORE_TOTAL` を桁区切りにした表示、全角入力の拒否例も確認した。保存済みのXMLとコンソールログで実装変更前の失敗2件と変更後の全24件の成功を確かめ、リファクタリングの見送りは妥当と判断した。修正が必要な指摘はなかった。

そらは素点の合計が99,000点になる例で、`confirmScores()` による入力の確認から合計エラーの表示までを説明した。小テストでオーナーは `calculateMatchResults()` が `RawScores` と `EXPECTED_SCORE_TOTAL` を使って合計を判定し、返されたエラー理由を `MatchFailureReason.message()` が文言に変換すると説明した。今回変えたのは文言を返す処理で、同じ入力は変更前後とも合計エラーになることをオーナーが自分の言葉で説明できたため、そらは合格とした。
