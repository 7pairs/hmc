# 0010 保存した半荘を見返せるようにする

## 目的と対象

素点入力画面から初期リーグの「半荘履歴」を開き、その日に保存した4〜5半荘を一覧で見渡せるようにする。照合したい半荘を選び、詳細で紙の記録と席ごとに突き合わせる。半荘の訂正とリーグ順位の表示は後続の作業で扱う。（参照：[手順書0009](0009-save-matches.md)・[プロジェクト憲章](../project-charter.md#実戦での試用と移行)）

## 手順

### 1. 半荘履歴の画面と読み出しの設計を決める

そらは一覧と詳細の画面案を作る。表示する日時には最初に「この半荘を保存」を押したときの時刻を使う。端末のタイムゾーンで23:59に押して保存に失敗し、翌日の00:01に再試行して成功した場合は、最初に押した日の23:59として表示する。（参照：[保存処理と入力状態](../specs/match-score-entry.md#保存処理と入力状態)）

一覧は端末のタイムゾーンで見た保存日ごとにまとめ、日付も日付内の半荘も新しい順に並べる。日付は午前0時に切り替わり、以前の日付の半荘には下へスクロールして移動できる。各行には保存時刻とトップの選手名を表示し、同着トップなら該当する選手全員の名前を表示する。

二人で、トップの名前を出す案と、4人の名前を着順で並べる案を比べる。同日の4〜5半荘を小さい画面に並べ、名前が長い場合や同着トップの場合も、時刻とトップの名前を読んで目的の半荘を探せるかを確かめる。採用する表示項目は画面案で比べたあとに決め、手順2に着手する前に二人で合意する。

詳細には保存した日時と、東・南・西・北の席順で選手名、素点、着順、成績ポイントを表示する。選手名は選手IDに対応する現在の表示名を使う。着順とポイントは、その半荘の素点と保存時に記録したルールから既存の成績計算で求める。（参照：[保存するデータと制約](../specs/match-score-entry.md#保存するデータと制約)・[半荘成績の計算仕様](../specs/match-results.md)）

入力画面で「選手を登録・変更」を押せる状態なら「半荘履歴」も開ける。保存中、保存結果の照合中、成否が不明なときや半荘IDが衝突したときは、入力画面で保存状態を表示して「半荘履歴」を無効にする。詳細から一覧へ戻るときは、開いた半荘が見える位置に戻す。一覧から入力画面へ戻るときは、選んだ席、素点、確認結果を保つ。履歴を開く前に保存できる状態だった半荘は、入力に戻ったあともそのまま保存できる。（参照：[半荘を保存する仕様](../specs/match-score-entry.md#半荘を保存する)）

そらは既存のRoomの記録をRepositoryから読み出し、Roomの型を画面に渡さずに成績を表示する方法を決める。保存済みの半荘が0件の場合と読み出しに失敗した場合に、画面で何を伝え、利用者が次に何をできるかも決める。半荘履歴の仕様・設計・テスト項目を `docs/specs/match-history.md` にまとめ、素点入力画面からの移動と復帰に関わる仕様を更新する。

うみは同日の半荘を探しやすいか、日付と時刻の扱いが明確か、改名やリーグのルール変更後も表示が合意した内容に沿うかを確認する。保存状態に応じた履歴への移動と、入力に戻ったあとにできる操作が明確かも確認する。二人で画面案と仕様・設計・テスト項目に合意する。

### 2. 保存した半荘の一覧と詳細を表示する

そらは手順1で合意したテスト項目に沿って、原則としてテストコードを先に書き、対象の動作が未実装のために失敗することを確かめる。既存のDBから初期リーグの半荘を読み出し、共通画面に一覧と詳細を表示する。素点入力画面から履歴への移動と、詳細から一覧、一覧から入力画面への復帰をつなぐ。（参照：[SDDのテストコードと本体の実装](../sdd/README.md#82-テストコードと本体の実装)）

`./gradlew :shared:testAndroidHostTest` で今回のテストと既存の共通テストを実行する。

- 保存の再試行を検証するため、`ChronicleState` にテストから時刻を変えられる `now` を渡す。23:59の初回保存ではテスト用のRepositoryから記録がないことを示す失敗を返す。時刻を翌日の00:01に進めて再試行し、Repositoryに渡る `savedAtMillis` が最初の23:59のままであることを確かめる。
- 履歴の日付分けでは表示に使うタイムゾーンを固定する。23:59と翌日の00:01に相当する `savedAtMillis` を持つ2件が別の日付に並び、翌日の分が上に来ることを確かめる。
- 同着トップの名前が全員分出ること、改名が保存済みの半荘にも反映されることを確かめる。リーグのルールを切り替えても、保存済みの半荘は保存時のルールで計算できることを確かめる。
- 状態ホルダーで、保存状態に応じて履歴を開けるかを確かめる。未入力や入力途中、保存の失敗が確定して再試行できる状態では開ける。保存中、照合中、成否が不明なとき、半荘IDが衝突したときは、履歴を開く操作をしても入力画面を示す状態と保存状態を保つ。

両OSの永続化テストでは、23:59と翌日の00:01に相当する `savedAtMillis` を別々の `MatchRecord` に指定し、Repositoryを通してテスト用DBに保存する。DBを開き直し、履歴の読み出しで指定した時刻を取得できることを確かめる。（参照：[AndroidとiOSでの永続化テスト](../specs/match-score-entry.md#androidとiosでの永続化テスト)）

うみは保存した半荘と4席、選手名、ルールの対応に加え、時刻の扱いと入力画面に戻ったときの状態を確認する。二人で実装の差分と検証・レビュー結果を確認する。

### 3. 両OSで履歴を検証してコードの構造を見直す

そらはAndroidとiOSのそれぞれで、手順書0009の時点のアプリで半荘を保存したDBを用意する。履歴を実装したアプリでそのDBを引き継ぎ、一覧の日付、時刻、トップの名前と、詳細の席順、選手名、素点、着順、ポイントを保存前に確認した内容と照合する。

両OSの小さい画面で、同日に保存した4〜5半荘を一覧で見渡せるか、名前が長い選手が同着トップでも時刻とトップ全員の名前を読めるかを確かめる。最初の表示では画面外にある過去日の半荘までスクロールして詳細を開き、一覧へ戻ったときにその半荘の行が見えることを確かめる。

両OSで保存中、照合中、成否が不明な状態、半荘IDが衝突した状態を再現する。入力画面にそれぞれの保存状態が表示され、「半荘履歴」が無効になっていることを確かめる。

次の半荘の席と素点を入力してから履歴を開き、入力画面に戻ったときに値が残ることを確かめる。成績を確認したあとにも同じ操作を行い、確認結果が残ることを確かめる。続けて「成績を確認」を押し直さずに保存し、次の半荘の席と素点が空欄になり、履歴の半荘が1件だけ増えたことを確かめる。検証に使った端末、OS、実行方法と結果を記録する。

二人でDBからの読み出し、成績計算、一覧と詳細の表示までのコードをたどる。オーナーは表示名と計算ルールをそれぞれどの記録から得るかを自分の言葉で説明する。コードを整理するかどうかとその理由を記録し、変更した場合は関係するテストを再実行する。うみは検証結果と構造を見直した判断を確認し、コードに変更があれば差分も確認する。

## 完了条件

AndroidとiOSで入力画面から半荘履歴を開き、保存日ごとの一覧から目的の半荘を探し、席順の詳細を確認できる。入力画面に戻って途中の入力や確認結果を使える。手順1で合意した検証、必要なレビューと再レビュー、構造と理解の確認、仕様文書と作業記録の更新が済んだことを二人で確認する。

### 草稿のレビュー

二人でうみの指摘3件を採用した。

1. 再試行でも最初に保存を押した時刻を使うため、履歴に表示する日時と午前0時をまたぐ例を明記した。時刻を引き継ぐテストと、保存済みの時刻から日付を分けるテストを手順2に加えた。
2. 入力画面で保存や照合の結果を追えるように、履歴を開く条件を「選手を登録・変更」とそろえた。確認済みの入力に戻ったあと、そのまま保存できることも両OSの検証に加えた。
3. 既存の記録を引き継げることと、実際の画面で目的の半荘を探せることを確かめるため、0009のDBを使う確認、長い同着トップ名の表示、スクロール後の一覧への復帰を両OSの検証に加えた。

うみは再レビューで初回の指摘3件が解消したことを確認し、保存状態の検証について改善を1点提案した。既存のテスト構成で確認する範囲を明確にするため、二人でこの提案を採用した。手順2では状態ホルダーで履歴を開ける条件と保存状態の維持を確かめ、手順3では両OSの入力画面で保存状態の表示を確かめる。

2回目の再レビューで、うみは改善案が手順2と手順3に反映されていることを確認し、追加の指摘はなかった。
