## 目的と対象

初回の実戦試用に向けて、卓で供託を精算したあとの素点を入力し、４人が名前と素点を見比べながら着順と成績ポイントを確認できるようにする。入力と確認はAndroidとiOSで共通の画面に置く。[プロジェクト憲章](../project-charter.md)

紙のスコアシートではその日の１半荘目の東・南・西・北の順に４人の列を決め、その後も同じ人の列に素点と席を書く。今回の画面では仮の４人を固定順に表示する。実際の選手の登録、その日の表示順の設定、端末への保存、リーグ順位への反映は後続の作業で扱う。保存を設計するときに、半荘ごとの席の記録方法も検討する。

## 手順

### 1. 素点入力と成績表示の仕様・設計・テスト項目を決める

[半荘の素点入力と成績表示の仕様・設計・テスト項目](../specs/match-score-entry.md)

そらは `docs/specs/` に素点入力と成績表示の仕様・設計・テスト項目をまとめ、この手順書から参照できるようにする。計算規則と計算時のエラー条件は既存の仕様を参照する。[半荘成績の仕様・設計・テスト項目](../specs/match-results.md)

素点欄は４人とも空欄で始める。欄に単位を示し、`35000` や `-1100` のように点単位の整数を入力する。「成績を確認」を押すと入力を検証し、計算に成功した場合は同じ画面に名前、桁区切りで表示した素点、着順、成績ポイントを入力と同じ順で表示する。素点を編集すると表示中の結果を消し、改めてボタンを押すと編集後の素点で計算する。

空欄や整数として読めない値は、該当する欄で知らせる。100点刻み、合計100,000点、３人以上の同着については、既存の計算が返す理由を画面に表示する。成績ポイントの正負と入力エラーは、符号や文言でも分かるようにする。共通画面の色は `MaterialTheme.colorScheme` から取り、色コードはテーマで管理する。今回の配色には既存のテーマを使う。

設計では入力欄の文字列と確認結果をどこで保持するか、入力をどこで整数に変換するか、計算結果を各人の表示にどう対応付けるかを決める。計算には既存の `calculateMatchResults` を使い、順位点にはMリーグ方式の値を渡す。入力・確認の動作のうち共通テストで確かめる項目と、両OSの画面で確かめる項目を決める。

テスト項目には通常の入力、負の素点、同点トップ、空欄と整数に変換できない入力、計算が返す３種類のエラー、確認後の編集と再計算を含める。そらは仕様を作業範囲と照合し、結果の期待値を既存の計算仕様と照らし合わせる。うみは仕様と設計が作業範囲に沿っているか、テスト項目で入力から確認までの動作を検証できるかを確認する。二人で検証とレビューの結果を確認し、仕様・設計・テスト項目に合意する。

### 2. 共通画面に素点入力と成績表示を実装する

そらは手順1で合意した共通テストを書き、`./gradlew :shared:testAndroidHostTest` で実行する。対象の動作が実装されていないためにテストが期待どおり失敗することを確かめ、対象のテストと失敗の内容を記録する。

そらは `shared/src/commonMain` のCompose画面に入力と成績表示を実装する。４人分の入力を検証して既存の計算に渡し、成功時の結果と失敗時の理由を表示する。実装後は同じGradleタスクを実行し、既存のテストと追加したテストの結果を記録する。

そらは画面の差し替えに合わせて、初期画面の仕様・設計・テスト項目のうち起動後の画面に関する記述を更新し、素点入力と成績表示の仕様への参照を加える。[初期画面の仕様・設計・テスト項目](../specs/initial-screen.md)

うみは入力した名前と結果の対応、編集時の結果の消去、計算の失敗理由の表示、テーマの色の参照、テストの期待値、起動後の表示と仕様文書の整合を確認する。二人で差分と検証・レビューの結果を確認する。

### 3. 両OSで画面を検証しコードの構造を見直す

そらはAndroidとiOSの実機またはエミュレータ・シミュレータでアプリを起動し、素点入力仕様の画面の検証項目を実施する。画面のキーボードで負の素点を入力できることと、名前と素点を照合できることを確かめる。縦の表示領域が狭い状態でキーボードを開いたままスクロールし、４欄と「成績を確認」に到達できることも確かめる。[両OSでの画面確認](../specs/match-score-entry.md#androidとiosでの画面確認)

成績を表示してから素点を編集する。編集した直後に「成績を確認」を押さず、古い結果が消えていることを確かめる。続けて４人分の素点を計算できる値にそろえ、改めて「成績を確認」を押す。編集後の素点に対応する着順と成績ポイントが表示されることを確かめる。検証した端末または仮想端末、OS、結果を記録する。

二人で既存の計算やOSごとの起動コードも含めて構造を見直す。画面での入力と結果表示、既存の計算、OSごとの起動処理のつながりをたどり、整理の要否と理由を記録する。コードを変更した場合は関係する検証を再実行する。うみは検証結果と構造を見直した判断を確認し、コードを変更した場合はその差分もレビューする。

そらは「成績を確認」を押してから画面に結果が出るまでをコードで説明する。オーナーはその流れをたどり、Composeで共有する画面と共通Kotlinの計算がそれぞれ何を担当するかを自分の言葉で説明する。二人で検証とレビューの結果を確認する。

### 手順1の作業記録

うみの指摘２件を二人で採用した。

- 有効な編集で素点の文字列が変わった時点で、表示中の成績と計算エラーを消す。元の値に戻しても成績が再表示されず、拒否された貼り付けでは成績が残ることをテスト項目に加えた。
- 起動後の表示と仕様をそろえるため、手順2で画面を差し替えるときに初期画面の仕様とテスト項目を更新することにした。

再レビューでうみは初期画面の仕様を更新する手順と編集後の検証項目が加わったことを確認した。修正案の `TextFieldValue` 版では、再コンポーズ前に素点を変えて元に戻すと、元に戻した編集の通知が届かない場合があると指摘した。二人で指摘を採用し、入力欄を `String` 版に変更する設計に改めた。再コンポーズを挟まない連続編集で素点が元に戻り、成績が消えたままであることをテスト項目に加えた。

次の再レビューでうみは `String` 版で通知の欠落が解消したことを確認した。無効な編集を拒否しても、再コンポーズ前は内部の入力バッファに変更が残り、直後の有効な入力まで失われ得ると指摘した。二人で指摘を採用し、`TextFieldState` と `InputTransformation` で無効な編集を確定前に取り消す設計に改めた。確認時からの入力欄の編集履歴で成績を表示するか判断し、再コンポーズを挟まず無効な編集のあとに有効な編集を送るケースをテスト項目に加えた。

うみは再レビューで、無効な編集を次の入力までに取り消せる設計になったことを確認した。回転時に入力値とともに編集履歴も復元されることを確かめるため、元に戻す操作のあとに画面を回転する提案を二人で採用した。古い成績が表示されず、やり直す操作が使えることを両OSの画面確認に加えた。

うみは最後の再レビューで、回転後の入力値と編集履歴の復元を確認できるテスト項目になったことを確かめた。追加の指摘はなかった。[回転後の確認項目](../specs/match-score-entry.md#androidとiosでの画面確認)

そらは仕様を作業範囲と照合し、着順、成績ポイント、計算エラーの期待値を既存の計算仕様と照らし合わせた。二人で検証とレビューの結果を確認し、仕様・設計・テスト項目に合意して手順1を完了とした。共通テストの実行は手順2、両OSでの画面確認は手順3で行う。

### 手順2の作業記録

`shared/src/commonTest/kotlin` に `ScoreConfirmationTest` を追加した。テストから呼び出す型と関数を用意し、成績やエラーを組み立てる処理を入れる前にテストを実行した。たとえば負の素点を含むケースでは、４人分の成績を期待するテストに空の結果が返り、アサーションが失敗した。既存の `MatchResultsTest` は12件すべて成功し、新規テストは12件すべて期待値との不一致で失敗した。

`shared/src/commonMain` に素点の検証と成績表示を追加した。共通のCompose画面は４つの入力欄を持ち、編集履歴に応じて成績とエラーの表示を切り替える。合計エラーの案内には計算と同じ `EXPECTED_SCORE_TOTAL` を使う。

実装前後ともAndroid Studio同梱のJBR 25.0.4を使い、`./gradlew :shared:testAndroidHostTest --console=plain --offline` を実行した。実装後は既存12件と新規12件の計24件が成功した。XMLレポートで両テストクラスの失敗・エラー・スキップが各０件であることを確認した。

初期画面の仕様・設計・テスト項目を、起動時に共通の素点入力画面を表示する内容に更新した。そらはAndroidとiOSの起動処理をコードでたどり、どちらも共通の `App()` から素点入力画面を表示することを確認した。画面での操作は手順3で確かめる。[初期画面の仕様・設計・テスト項目](../specs/initial-screen.md)

うみは、Androidでキーボードが開いていると下の入力欄や確認ボタンが隠れる可能性を指摘した。二人で指摘を採用し、共通画面がキーボードの領域を避けられるよう、`MainActivity` に `android:windowSoftInputMode="adjustResize"` を指定した。`./gradlew :androidApp:processDebugMainManifest --console=plain --offline` が成功し、Debug用のマージ済みManifestに指定が反映されたことを確認した。キーボードを開いたまま４欄とボタンに到達できることは手順3で確かめる。[Androidのエッジツーエッジ設定](https://developer.android.com/develop/ui/compose/system/setup-e2e#configure-windowsoftinputmode)

うみは再レビューで `adjustResize` がDebug用のマージ済みManifestに反映され、キーボードを開いたまま操作する確認項目が仕様と手順3に記載されていることを確かめた。指摘は解消し、追加の指摘はなかった。

二人で実装と文書の差分、共通テスト、Manifestの検証、レビューの結果を確認し、手順2を完了とした。
